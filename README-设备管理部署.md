# 售后雷达 Pro 6.2 设备管理

## 这一版改了什么

**登录流程（修复真实漏洞）**

6.1 里只有「点登录按钮」这一条路径做了设备检查，另外两条路径直接放行：

- 刷新页面：`init()` 发现本地有登录状态就直接进应用，不查设备。
- 登录事件：`SIGNED_IN` 事件里直接 `show()`，和设备检查是抢跑关系，被封设备会短暂进入应用，签出后界面还停在应用里。

现在三条路径统一走 `enterApp()`：先调用 `security_register_device`，通过才显示应用；被封、被拒、网络/RPC 异常一律不放行。进入应用后每 2 分钟、切回页面、网络恢复时会复查，设备被封后最迟约 2 分钟被踢回登录页。被封设备退出时用 `signOut({scope:"local"})`，不会把同账号的其他正常设备一起踢下线。

**管理员后台新增「设备」**

显示邮箱、设备名称、设备 ID、平台、App 版本、状态、创建时间、最后在线、封禁时间、封禁原因、操作人。可搜索、可封禁（必须填原因、二次确认）、可解封，操作后自动刷新。当前设备不显示封禁按钮。

## 部署步骤

前端（`index.html`）已经提交，GitHub Pages 会自动更新，不需要额外操作。

数据库（Supabase -> SQL Editor），按顺序：

1. 打开 `supabase/device_security_diagnostics.sql`，**一条一条**执行，把结果发给我（里面没有密钥，不含公钥）。重点是 A、B、C、D 四项。
2. 打开 `supabase/device_admin.sql`，把第 1、2、3 段**分别单独粘贴、单独 Run**，不要整份一次粘贴。
3. 第 4 段（锁死 `security_devices` 直接写入）先不要执行，等诊断结果确认 `security_register_device` 是 `security definer` 之后再执行。

如果又出现 `42601 syntax error at or near ")"`：

- 一次只粘一个 `create or replace function`，必须从 `create` 复制到 `$fn$;` 结束，不能少最后一行。
- 手机输入法可能把 `$`、引号或括号替换成全角/弯引号，建议从 GitHub 文件页长按复制，不要手敲。
- 仍然失败就把 SQL Editor 报错里的行号和当时粘贴的内容截图发我。

## 测试步骤（手机上做）

1. 用管理员账号登录 -> 更多 -> 管理后台 -> 设备，应能看到所有设备，本机标注「本机」且没有封禁按钮。
2. 用**另一个普通测试账号**（或另一个浏览器）登录一次，让它产生一条真实的 `WEB-…` 设备记录。
3. 回到管理员设备页，封禁那条记录：不填原因应被拒绝；填原因后确认，列表刷新并显示「已封禁」和操作人。
4. 在被封的浏览器里**刷新页面**：应直接回到登录页并提示「此设备已被禁止登录」。
5. 在被封浏览器里重新输入账号密码登录：同样被拦下，且全程不会短暂看到应用界面。
6. 管理员解除封禁后，被封浏览器可以重新登录。
7. 用普通账号登录：顶部不应出现「管理」按钮。服务端对非管理员调用 `admin_list_devices` / `admin_set_device_status` 应返回 `forbidden`，这一项在手机上没法直接模拟；连接 Supabase 连接器后由我用真实的非管理员身份验证。

注意：之前被封的 `WEBTEST-…` 是「设备注册诊断」按钮生成的 ID，不是登录用的 `WEB-…`，所以那次封禁没有测到真实登录流程，请按上面第 2~5 步重新测。

## 已知限制（请知悉）

- 网页端的设备 ID 存在浏览器 `localStorage`，清除浏览器数据后会生成新的设备 ID，被封的人可以靠这个绕过。网页端无法做到真正的设备绑定；要强约束应增加「按账号封禁」，或把应用做成带原生硬件密钥的 App。
- `public_key` 目前是前端生成的占位字符串，不是真实的硬件密钥，也不是真正的设备证明。
- 设备封禁目前只在前端（`enterApp`）强制执行；数据表的 RLS 只校验 `user_id = auth.uid()`，没有校验设备状态。也就是说，被封设备如果绕过前端直接用 API，仍然可以读写该账号自己的数据。
- 管理员「不能封自己当前设备」在前端按钮和数据库函数里都做了限制，但数据库里依赖前端传来的 `current_device_id`，它的作用是防止误操作，不是安全边界；没有传这个值时，数据库会拒绝封禁管理员自己名下的任何设备。
